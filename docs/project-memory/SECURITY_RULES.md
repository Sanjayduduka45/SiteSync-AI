# SECURITY RULES — SiteSync AI

> These rules are **non-negotiable**. Any change to security boundaries requires explicit human approval and change control.

---

## 1. Secrets and Credentials

- **Secrets are only supplied via environment variables.** No hardcoded secrets anywhere.
- **Never commit secrets, API keys, tokens, passwords, or connection strings to Git.** This includes test credentials.
- `.env` files are **never committed**. They are listed in `.gitignore`.
- `.env.example` files are committed with **placeholder values only** (e.g., `SUPABASE_URL=your_supabase_url_here`).
- If a secret is ever accidentally committed, it must be treated as compromised and rotated immediately.

---

## 2. Authentication

- Authentication is handled by **Supabase Auth**.
- All API requests from the frontend must carry a valid **Supabase Auth JWT** as a `Bearer` token.
- The backend validates the JWT on **every** API request.
- The backend does not trust any client-supplied user identifier (e.g., `user_id` in a request body) — only the identity asserted by the validated JWT.

---

## 3. Authorization

- **Server-side authorization is mandatory.** Never rely on client-side authorization alone.
- Every API endpoint enforces role and project membership checks after JWT validation.
- **Supabase Row-Level Security (RLS) is enabled** on all tables as a defense-in-depth layer.
- RLS policies must be tested as part of any database schema change.
- A user can only access data in projects they are authorized for.
- Planner-only actions (approve/reject/modify) are enforced at both API and RLS layers.

---

## 4. AI Authorization Boundaries

- **AI must not bypass authorization.** All AI-triggered database operations go through the authorized API layer.
- **AI must not directly perform privileged database operations.** AI pipeline returns recommendations as structured data; the API layer writes them.
- **AI recommendations never become approved actuals without a planner decision.** No background process auto-approves.
- AI-generated content is treated as untrusted until a human planner signs off.

---

## 5. Input Validation

- **All inputs are validated via Pydantic v2 schemas** on the backend before any processing.
- Input validation happens on the server, not just the client.
- File uploads are validated for type, size, and content before storage.
- Maximum file size limits are enforced.
- Allowed file types are explicitly allowlisted (not denylisted).

---

## 6. AI Output Validation

- **AI outputs are validated against strict Pydantic schemas** before use.
- If an AI response does not conform to the expected schema, the failure is surfaced to the planner — never silently dropped or auto-corrected in a way that creates false data.
- AI output is treated as untrusted external input until validated.
- Prompt injection risks are mitigated by:
  - Never inserting raw user input directly into LLM prompts without sanitization.
  - Using structured output formats (JSON mode / function calling) where available.
  - Validating all LLM outputs against schemas.

---

## 7. File Handling

- Files are stored in **Supabase Storage**, not in the database.
- Files are accessed via **signed URLs** generated by the backend, not served directly.
- Signed URLs must have appropriate expiry times.
- File paths and metadata are stored in the database; file access is always mediated by the backend.
- No direct public file access without authorization check.

---

## 8. Audit Log

- The audit log is **append-only**. Rows are never deleted or updated.
- Every field input submission, AI extraction, and planner decision is logged.
- Audit entries include: timestamp, user ID, project ID, action type, and relevant record IDs.
- Audit log access is restricted to authorized roles.

---

## 9. Data Exposure

- API responses return only the data the requesting user is authorized to see.
- Error messages do not expose internal system details, stack traces, or database structure to the client.
- Verbose error details are logged server-side only.

---

## 10. Transport Security

- All communication is over **HTTPS** in production.
- No HTTP in production.
- Supabase connections use TLS.

---

## 11. Dependency Security

- Dependencies are pinned to specific versions.
- `requirements.txt` (backend) and `package.json` lock files (frontend) are committed.
- No unknown or unreviewed dependencies are added without justification.

---

## Change Control for Security Rules

Any change to these security rules requires:
1. Explicit human approval.
2. Documentation of what changed and why.
3. Assessment of what is affected.
4. Update to this document.

Do not modify security rules automatically.
